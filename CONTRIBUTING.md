# Вклад в GameBot

Для локальной разработки нужны Windows и Python 3.11+. Подготовка окружения
и команды проверки описаны в [руководстве разработчика](docs/development.md).

## Как предложить изменение

1. Для крупного изменения сначала создайте issue и опишите задачу.
   Небольшое исправление можно сразу отправить pull request.
2. Нажмите **Fork** на странице репозитория, затем клонируйте свою копию.
3. Создайте отдельную ветку, например `fix/fishing-pause`.
4. Подготовьте окружение по руководству разработчика, внесите изменение
   и выполните проверки ниже.
5. Создайте коммит и отправьте ветку в свой fork.
6. Откройте pull request из своей ветки в `ansalim01/bot-gta-5-majestic:main`.
   Укажите проблему, итоговое поведение и результаты проверок.

```powershell
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
.\.venv\Scripts\python.exe -m pytest
```

GitHub Actions повторит проверки для Python 3.11 и 3.13 в pull request.
Ссылка на журнал доступна на вкладке **Checks**. Если проверка упала,
исправьте причину и отправьте новый коммит в ту же ветку: PR обновится автоматически.

Для первого PR из внешнего fork владелец может сначала разрешить запуск
через **Approve and run workflows**. Это разрешение запуска тестов,
а не одобрение изменения для слияния.

## Как принимаются изменения

Владелец всех файлов указан в `.github/CODEOWNERS`: **@ansalim01**.
Для изменений участников в `main` требуются успешные проверки
`checks (3.11)` и `checks (3.13)`, одобрение владельца и закрытые обсуждения.
Ветка должна учитывать актуальный `main`. Новые коммиты отменяют предыдущее
одобрение и требуют повторного просмотра.

После проверки владелец принимает PR вручную. Автоматического слияния нет.
Порядок действий для владельца описан в [руководстве сопровождения](docs/maintaining.md).

## Работа с кодом

Перед изменением игрового поведения воспроизведите проблему на сохранённом
кадре или искусственной последовательности состояний. Добавьте тест, который
падает на исходной реализации, затем исправляйте код. Для рефакторинга сохраняйте
порядок действий, задержки и формат событий.

Используйте Ruff для оформления кода. Давайте функциям имена по действию,
которое они выполняют; комментарии должны объяснять ограничения игры и причины
решения. Не объединяйте исправление игрового алгоритма с массовым форматированием.

Новый сценарий подключается через отдельную задачу, точку входа и метаданные
панели. Последовательность подключения описана в [архитектуре](docs/architecture.md).
Настройки пользователя хранятся отдельно от общих YAML; не добавляйте в изменения
свои локальные настройки, журналы, записи игровых сессий или временные инструменты.

В pull request укажите проблему, итоговое поведение, выполненные проверки и
результат ручной проверки в игре, если менялись распознавание, ввод или тайминги.
